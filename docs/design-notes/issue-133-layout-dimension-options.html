Design note · ha-teamtracker-scoreboard-card

Flat card options for the remaining fixed row dimensions

Issue #133 Slug layout-dimension-options Status approved Type feature Slices 2

Problem

#132 made the team-name column width configurable through a --scoreboard-team-col-width custom property on <ha-card> with a 99px fallback baked into the stylesheet. Every other horizontal and vertical dimension of a row is still a bare constant in src/styles.ts: .logo is 30px wide, .score 34px, .colon 9px, and .game-row plus the .logo / .score / .colon cells are all 28px tall (with the <img> at 28×28). A user who wants bigger logos, a denser row, or wider scores for three-digit basketball totals has to fork the card.

#132 also left separate widths for team column A vs B explicitly out of scope. The grill folded that back in here — but as one option, team_width, that takes either a single length (both columns) or a two-element list (A, then B), superseding team_col_width as the documented name.

Prior art

LESSONS.md already carries the entry this change must obey — "Test for a CSS-custom-property-backed option fails/passes misleadingly on shadowRoot.innerHTML" (#132). Its guardrail names this issue directly: for --scoreboard-* options, assert on card.shadowRoot.querySelector("ha-card").getAttribute("style"), not innerHTML (the stylesheet's var(…, fallback) is always in innerHTML), and pair it with a CARD_STYLES-contains assertion for the stylesheet side. test/index.test.ts › "team_col_width" and test/snapshot.test.ts › CARD_STYLES wiring are the templates to copy.

Nothing else here has been fixed-and-guarded. This is additive capability on the #132 pattern, not a regression.

Decision from the grill

Shape Flat sibling options, not a dimensions: map. team_col_width shipped flat in #132 and cannot move into a map without a breaking change; a map would split the layout knobs across two places. Cost accepted: five more top-level keys.
  • Every option is a CSS length string and defaults, when unset, to today's constant via the stylesheet fallback. No config validation (consistent with height, team_col_width, rank_type — a shared validator is a separate pre-existing gap).
  • row_height drives everything vertical — .game-row, the three cell heights, and the <img> height. A taller row gets a taller logo; object-fit: contain keeps the logo's aspect ratio, so a non-square box just adds padding rather than distorting.
  • logo_width sizes the <img> too, not only the .logo container — otherwise the knob half-works (a wide container with a stranded 28px image).
  • One team-column option, scalar or pair. team_width: 130px sets both; team_width: [130px, 90px] sets A then B. _render normalises to two values and emits --scoreboard-team-col-a-width / -b-width; the stylesheet nests var(--…-a-width, var(--scoreboard-team-col-width, 99px)) so the #132 property still resolves. team_col_width stays as a silent single-value alias — #132 configs keep working, team_width wins if both are set.
  • .team-pos (18px) is not exposed. #132 kept it deliberately narrow; a position_width knob is a one-line follow-up if it is ever wanted.
  • getCardSize() reads row_height — parseInt with a 28 fallback, mirroring how it already parses height, so the Lovelace layout estimate stays honest for tall/short rows.

Design it twice

Axis 1 — emitting the growing set of custom properties in _render

Chosen

A · A cssVars table

One object literal mapping property name → option value, reduced to a string of the entries that are set. team_col_width moves into it. 

// normalise the team-column option first: scalar | [a, b] | legacy alias
const tw = team_width ?? team_col_width;
const [aW, bW] = Array.isArray(tw) ? tw : [tw, tw];

const cssVars = {
  "--scoreboard-team-col-a-width": aW,
  "--scoreboard-team-col-b-width": bW,
  "--scoreboard-logo-width": logo_width,
  "--scoreboard-score-width": score_width,
  "--scoreboard-colon-width": colon_width,
  "--scoreboard-row-height": row_height,
};
const varStr = Object.entries(cssVars)
  .filter(([, v]) => v)
  .map(([k, v]) => `${k}:${String(v)};`)
  .join("");
  • Adding a knob is one line; the property/option pairing is scannable in one place.
  • The scannability is exactly what the #132 LESSONS.md entry asks for.
  • ~8 LOC net over the status quo.
Rejected

B · Keep appending template fragments

Continue the current style: ${x ? `--scoreboard-x:${x};` : ""} concatenated onto haCardStyle, once per knob.

  • Zero abstraction, matches what is there now — for one knob.
  • The haCardStyle line is already ~200 chars with height + position:relative + team_col_width; six more triples make it unreadable and typo-prone (a wrong var name or missing ; fails silently).

Axis 2 — one team_width (scalar or pair) vs two A/B options

Chosen

A · team_width: string | [string, string]

One option. _render normalises — Array.isArray(tw) ? tw : [tw, tw] — and always emits --scoreboard-team-col-a-width / -b-width. The stylesheet nests the fallback: .team-col-a { width: var(--…-a-width, var(--scoreboard-team-col-width, 99px)); } (mirror for -b), so the #132 property is still a live alias. team_col_width feeds the same tw when team_width is absent.

  • "Both = X" and "A, B differ" are one option, one mental model.
  • Cascade order (per-side → shared → 99px) stays in CSS; JS just emits whatever is set.
  • The list shape reads naturally in YAML and needs no delimiter parsing.
Rejected

B · Separate team_col_a_width / team_col_b_width

Two more flat options alongside the existing team_col_width.

  • Three option names for one concept; "make both 130" still has to reach for the old name.
  • More surface in the table, the types, the tests — for the rarer case.
  • A two-token string ("130px 90px") was also considered and dropped: it needs split/trim parsing and invites "1px solid"-style mistakes.

Slices

Slice 1 — the four symmetric knobs + cssVars + getCardSize

logo_width, score_width, colon_width, row_height. Introduces the cssVars table in _render and the getCardSize() tweak. team_col_width keeps emitting --scoreboard-team-col-width exactly as it does now (its normalisation moves in Slice 2), so this slice is behaviour-neutral for existing configs. Self-contained.

Slice 2 — team_width (scalar or pair) + team_col_width alias

Add team_width to the type; normalise team_width ?? team_col_width to [aW, bW] in _render and emit --scoreboard-team-col-a-width / -b-width. Replace the shared .team-col width rule with per-side .team-col-a / .team-col-b rules nesting the fallback to --scoreboard-team-col-width then 99px. README: document team_width, mark team_col_width deprecated, note that asymmetric columns move the score off the horizontal centre.

Design invariants touched

None. All three CLAUDE.md invariants (season sort, one-row-per-game, HTTPS-only logos) and the #132 .team-pos gutter rule are untouched. The change is purely additive; with no option set, CARD_STYLES resolves to the same pixel values it does today. The Architecture Notes gain a line pointing at the cssVars table as the single place card-level layout properties are emitted.

Adjacent opportunities

  • A typography / font-size scale — .team-name 13px, .score 20px, .team-rank 9px, .message 13px and the rest are all fixed. A coherent font_scale or per-role family is a genuinely separate feature (readability, not layout fit). Filed as #136.
  • position_width for the .team-pos gutter — one line on this same mechanism, deliberately skipped here; revisit only if #134's outcome leaves it wanted.
  • Config validation for length / enum options — still absent card-wide; row_height: "banana" yields an invalid declaration the browser drops to auto. Same call as #130 / #132: out of scope, no validator layer.

This change makes the typography scale cheap (same cssVars table) and forecloses nothing.
