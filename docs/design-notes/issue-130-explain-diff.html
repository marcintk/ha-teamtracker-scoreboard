A config override for the standings-vs-fixtures decision

Prepared 2026-09-06 · PR #131

Background

The card shows one of two things for a section: a standings table, where teams are ranked by their win-loss record, or a fixture table, where rows are one-per-game and sorted by date. Which one you get is decided automatically, and until now there was no way to say otherwise.

The decision lives in one small function, resolveSortMode in src/sorting.ts. It looks at every tracked sensor and reads the season attribute that the underlying ha-teamtracker integration publishes. The rule was simple:

If any sensor reports a season that is set and is not the exact string "regular", show the fixture table. Otherwise, rank by the section's rank_type.

The reasoning behind that rule is sound. During the regular season a league table is what you want. During playoffs, cups and tournaments a table means little — you care about who plays whom and when — and those periods report season values like post or playoffs. Treating anything that isn't regular as "not the regular season" is a reasonable default when the season values are clean tokens.

The trouble is that not every league publishes a clean token. TeamTracker's Italian Serie A sensors report:

State:  PRE
League: SERA / Italian Serie A
Season: 2026-27-italian-serie-a

Here season is a descriptive slug, not a season-type. It is set, and it is not "regular", so the old rule flipped Serie A into the fixture table for the entire regular season, and nothing in the card's configuration could correct it. The opposite mistake is possible too: a user who wants the fixture table for a league the heuristic leaves in standings mode had no lever to pull.

The idea

Rather than try to make the automatic guess smarter — teaching it which slugs mean "regular" — this change adds a manual override. A new per-section option, season_mode, with three values:

ValueEffect
autoThe default. Exactly today's behaviour: fixture table when any sensor's season is set and not regular.
regularAlways rank by rank_type, whatever season says.
by-dateAlways the date-sorted fixture table, one row per game.

So the Serie A fix is one line of YAML:

sections:
  - name: Serie A
    prefix: sensor.sera_
    rank_type: win-draw-loss
    season_mode: regular   # the sensor's season label isn't a clean token

The mechanism is a pair of short-circuits at the very top of resolveSortMode, before it looks at any sensor:

season_mode
→
by-date?
return "by-date"
→
regular?
return rankType
→
else: scan sensors
(the old heuristic)

Because a forced mode returns before the sensor scan, it never depends on what the sensors say — which is the whole point.

Two smaller decisions are worth calling out. First, the default value is auto, so every existing configuration behaves byte-for-byte as before; this is purely additive. Second, an unrecognised value — a typo like season_mode: fixtures — falls through to the auto branch rather than throwing. That matches how the neighbouring rank_type option is already handled: the card has no config-validation layer, and this change doesn't introduce one.

The change in code

Three production files, twelve lines net.

src/types.ts

A new string-union type and one optional field:

export type SeasonMode = "auto" | "regular" | "by-date";

export interface SectionConfig {
  // ...
  season_mode?: SeasonMode;
}

The union deliberately mirrors the shape of the existing SortMode type next to it — three fixed values, no open-ended string.

src/sorting.ts

resolveSortMode gains a fourth parameter with a default, and two guard clauses:

export function resolveSortMode(
  entities: string[],
  states: HassStates,
  rankType: SortMode,
  seasonMode: SeasonMode = "auto",
): SortMode {
  if (seasonMode === "by-date") return "by-date";
  if (seasonMode === "regular") return rankType;
  return entities.some((id) => {
    const s = states[id]?.attributes?.season;
    return s && s !== "regular";
  })
    ? "by-date"
    : rankType;
}

The = "auto" default means callers that pass three arguments — and any code path that doesn't set the option — are unaffected. The order of the two ifs doesn't matter: "by-date" and "regular" are mutually exclusive.

src/render.ts

sectionHtml already destructures the section's options with defaults (limit = 10, rank_type = "win-draw-loss", and so on). One more line joins them, and the value is handed to the function:

const { /* ... */ season_mode = "auto" } = section;
// ...
const sortMode = resolveSortMode(entities, states, rank_type, season_mode);

Everything downstream is untouched

Deduplication, the one-row-per-game collapse, and the home-sensor-wins-over-away rule all live further down the render path and only ever run when sortMode === "by-date". They neither know nor care how that value was chosen, so they needed no changes.

Guardrail

A new describe("seasonMode override") block in test/sorting.test.ts pins the three behaviours that matter: regular beats a descriptive season label, by-date beats season: "regular", and an unrecognised value falls through to the heuristic in both directions. Coverage stays at 100%.

Docs

The README gets a row in the Section options table and a new "Season mode" subsection; the design-invariant line in CLAUDE.md gains a clause noting the override exists and that auto preserves the old behaviour.
